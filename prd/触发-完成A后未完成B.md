# PRD：推送任务 - 触发类型「触发-完成A后未完成B」

## 1. 功能概述

「触发-完成 A 后未完成 B」是一种针对用户行为缺口的精准召回触发方式。当用户完成事件 A（或 A 事件组合）后，在配置的时间窗口内**未完成**事件 B（或 B 事件组合），系统则对该用户进行推送触达。

典型应用：加购未支付、注册未完善资料、浏览未下单等漏斗缺失场景。

---

## 2. 使用场景

- 用户加入购物车后 2 小时内未完成支付，推送「购物车提醒 + 限时优惠」
- 用户完成注册后 1 天内未完成身份认证，推送「认证引导」
- 用户浏览商品详情后 30 分钟内未下单，推送「同款推荐」

---

## 3. 功能模块

该触发类型在「触发-完成 A」基础上，增加了 **B 事件配置**和 **A→B 时间窗口**两个模块。完整配置分为以下五个部分：

### 3.1 触发规则（A 事件配置）

与「触发-完成 A」中的 A 事件配置完全一致，详见对应 PRD。

核心字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| events | 数组 | 是 | A 事件列表，至少 1 个 eventName 不为空 |
| eventLogic | 枚举 | 是 | 多事件关系：`and` / `or` |
| eventTimeWindow | 整数 | 是 | 事件时间窗口数值 |
| eventTimeWindowUnit | 枚举 | 是 | `natural_day` / `natural_week` / `natural_month` |

单个事件字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| eventName | 字符串 | 事件名称，从系统列表选择 |
| countType | 枚举 | `total_count` / `first_time` / `last_time` |
| countOperator | 枚举 | `>=` / `=` / `<=` / `>` / `<` |
| countValue | 整数 | 计数值，最小 1 |
| filters | 数组 | 字段级过滤条件（可选） |

---

### 3.2 B 事件时间窗口（A→B 间隔）

定义从用户完成 A 事件起，等待其完成 B 事件的最大时间跨度。超过该时间窗口仍未完成 B，则触发推送。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| timeWindow | 整数 | 是 | 时间窗口数值，最小 1 |
| timeWindowUnit | 枚举 | 是 | `hours`（小时）/ `days`（天） |

**界面展示**：「完成 A 后 **[N]** **[小时/天]** 内未完成以下事件」

---

### 3.3 B 事件配置（未完成条件）

配置用户需要「未完成」的目标事件。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| bEvents | 数组 | 是 | B 事件列表，至少 1 个 eventName 不为空 |
| bEventLogic | 枚举 | 是 | 多 B 事件关系：`and` / `or` |

单个 B 事件字段（与 A 事件结构相同）：

| 字段 | 类型 | 说明 |
|------|------|------|
| eventName | 字符串 | 事件名称，从系统列表选择 |
| countType | 枚举 | `total_count` / `first_time` / `last_time` |
| countOperator | 枚举 | `>=` / `=` / `<=` / `>` / `<` |
| countValue | 整数 | 计数值，最小 1 |
| filters | 数组 | 字段级过滤条件（可选） |

> **注意**：B 事件配置中**不展示事件时间窗口**选项（hideTimeWindow = true），时间约束由上方 A→B 时间窗口统一控制。

---

### 3.4 触达时机

A 事件满足且时间窗口到期（B 未完成）后，对用户进行触达的时间策略。

| 配置项 | 类型 | 说明 |
|--------|------|------|
| deliveryTiming | 枚举 | `immediate`（立即）/ `delay`（延迟） |
| delayValue | 整数 | 延迟时长，最小 1；仅 delay 模式有效 |
| delayUnit | 枚举 | `minutes`（分钟）/ `hours`（小时）/ `days`（天）；仅 delay 模式有效 |

此处「立即」的语义为：时间窗口到期时立即发送（而非 A 完成后立即发送）。

---

### 3.5 起止时间

任务生效时间范围，仅在此期间内完成 A 事件的用户才纳入判断流程。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| startDate | 日期（YYYY-MM-DD） | 是 | 开始日期，不能早于今天 |
| startTime | 时间（HH:mm） | 是 | 开始时间，默认 00:00 |
| endDate | 日期（YYYY-MM-DD） | 是 | 结束日期，不能早于今天 |
| endTime | 时间（HH:mm） | 是 | 结束时间，默认 00:00 |

**校验规则**：startDate 不能晚于 endDate。

---

### 3.6 参与限制

控制同一用户在任务有效期内被触发推送的次数上限。

| 配置项 | 说明 |
|--------|------|
| 参与 1 次 | 用户只会被触发一次（frequencyEnabled = false） |
| 参与多次 | 用户可被多次触发（frequencyEnabled = true） |

选择「参与多次」时展示：

| 字段 | 类型 | 说明 |
|------|------|------|
| naturalDays | 整数 | 时间窗口（自然日数），最小 1 |
| maxCount | 整数 | 窗口内最多参与次数，最小 1 |

语义：「同一个用户 **N** 自然日内，最多参与 **M** 次」

---

## 4. 完整触发逻辑

```
任务生效期间（startDate ~ endDate）
    ↓
用户完成事件 A（满足 A 事件配置的条件）
    ↓
开始倒计时（timeWindow 小时/天）
    ↓
倒计时期间：
    ├── 用户完成了 B 事件 → 不发送推送，流程结束
    └── 倒计时结束，用户仍未完成 B 事件
            ↓
        检查参与限制（frequencyEnabled）
            ↓
        满足频次限制 → 立即/延迟发送推送
```

---

## 5. 表单校验规则

| 校验项 | 规则 |
|--------|------|
| 起止时间 | startDate 和 endDate 均不能为空 |
| 起止时间顺序 | startDate ≤ endDate |
| A 事件 | 至少 1 个事件的 eventName 不为空 |
| B 事件 | 至少 1 个 B 事件的 eventName 不为空 |
| A→B 时间窗口 | timeWindow 不能为空且 > 0 |
| 参与限制（多次） | naturalDays > 0，maxCount > 0 |

## 8. 与「触发-完成A」的差异对比

| 维度 | 触发-完成A | 触发-完成A后未完成B |
|------|-----------|-------------------|
| 触发条件 | 完成 A 事件 | 完成 A 事件 + 时间窗口内未完成 B 事件 |
| B 事件配置 | 无 | 必填，至少 1 个 |
| 时间窗口（A→B） | 无 | 必填（小时/天） |
| 触达时机语义 | A 完成后立即/延迟 | B 窗口到期后立即/延迟 |
| 适用场景 | 行为激励、完成奖励 | 流失召回、漏斗补全 |

---

## 9. 边界与限制

- 事件列表来源于后端接口 `GET /api/v1/push-tasks/events`，A 事件和 B 事件使用同一事件池
- B 事件不支持配置独立的时间窗口，统一由 A→B 时间窗口（timeWindow / timeWindowUnit）控制
- A→B 时间窗口单位仅支持「小时」和「天」（不支持自然周/自然月）
- 若用户在时间窗口内完成了 B 事件，即使后续又「未完成」，也不再触发（一旦满足 B 即豁免）
- 参与限制默认为「参与 1 次」（frequencyEnabled = false）
- 延迟推送时，若任务在延迟等待期间超过 endDate，是否推送由后端策略决定
